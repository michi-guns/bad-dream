# Reconcile conflicting context

Protocol: `reconcile-context` 2.0.0. Authority order is in
[foundation](../foundation.md); authority also depends on the fact being checked.

1. Identify claims, source paths/URLs, exact revisions, statuses and scope.
   Distinguish differing scope, a hypothesis, new evidence and pending integration
   from a true contradiction.
2. When an operator's request appears to rely on a misremembered workflow,
   verify and cite the established rule, then explain the discrepancy before
   treating the request as an override. Correct the procedure without assuming
   the person remembers the repository. If they accept the correction, use the
   established flow. If they insist after being informed, determine whether they
   intend a permanent amendment or a scoped exception; ask only if unclear.
   Follow [change-protocol](change-protocol.md) to record it. Do not re-challenge
   an already clear, informed change instruction.
3. Check current informed explicit operator direction, accepted proposal scope/revision,
   current protocols and the appropriate authority. Clear authority resolves
   routine work without redundant approval. Record the discrepancy and resolution.
4. If genuinely ambiguous, describe the concrete conflict and ask one focused
   question about the unresolved scope. Continue unrelated safe work. Do not pick
   whichever text has the newest timestamp.
5. Keep material alternatives exploratory unless explicitly directed or accepted.
   Preserve contrary evidence and propose reconsideration of accepted hypotheses.
6. When a decision changes, retain old rationale and mark it superseded. Link its
   replacement, reason, date and actual acceptance provenance; add reciprocal links
   where useful. Use body links or optional `supersedes`/`superseded_by` properties.
7. Inspect affected notes, chapter protocols, roadmap and tasks. Update routine
   references within scope. Review task validity; do not silently cancel, erase or
   complete it. Record unresolved dispositions.
8. Reload relevant instruction caches after protocol changes. Reconcile stale
   handoffs before applying them.

Historical chat is a lead, not current policy. Do not require deleting old chats,
promise that archive/delete clears memories, or automate retention. Flag a specific
obsolete memory only when relevant; mutate chat/memory only through an authorised,
verified supported action.

Expected examples: an old chat loses to a scoped accepted decision; newer
brainstorming remains exploratory; ambiguous accepted scope needs only that scope
resolved; an accepted change awaiting integration is applied within scope even
when the book still says otherwise. Disposable exercise evidence belongs in the
verification report, never in production acceptance records.
